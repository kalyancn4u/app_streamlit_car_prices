# 🛠️ Design Notes & Engineering Rationale

This document explains **the design decisions behind the app** — *what* each part
does, *why* it works the way it does, and *how* the pieces fit together. The
user-facing instructions live in [`README.md`](../README.md); this file is the
engineering deep-dive.

> **TL;DR** — The app is **data-driven from a single `metadata.json` contract**:
> one training run describes the entire UI, so the form can never drift from the
> model. Prices are handled in **Lakhs** end-to-end, every real category
> (including the common baselines like *Dealer* and *CNG*) is selectable, and the
> Random Forests are **regularised and compressed** so they stay small and load
> fast.

---

## 1. Design principles

Three ideas run through the whole project:

1. **One source of truth.** Everything the UI needs is generated by
   `train_model.py` into `metadata.json`. The apps render themselves from it, so
   retraining automatically refreshes the form — no hand-edited option lists.
2. **Make invalid states unrepresentable.** Because the data is clean and
   finite, the form only ever offers values that exist. Wrong input isn't
   *caught* after the fact — it can't be entered (see §6).
3. **Correct by construction, small by design.** Money is one consistent unit
   (Lakhs) throughout; the models are bounded and compressed so they generalise
   well and start quickly.

## 2. The data contract: knowing the dataset cold

Two properties of the Cars24 dataset shape almost every downstream decision.

### 💷 Prices are expressed in Lakhs — handled as Lakhs end-to-end

The dataset's `selling_price` column is in **Lakhs of Rupees**, not raw rupees:

```
selling_price = 1.2   ->  ₹1.2 Lakhs  (₹120,000)
selling_price = 5.5   ->  ₹5.5 Lakhs  (₹550,000)
```

Every component treats price as Lakhs consistently: `format_lakhs()` renders any
value in Indian **Crore / Lakh / Rupee** notation (1 Lakh = ₹100,000;
100 Lakhs = 1 Crore), the price-band edges (already in Lakhs) are used directly,
and `range_config.json` carries an explicit `"price_unit": "Lakhs"` so the
contract is **self-documenting** rather than implicit. A model output of `4.75`
therefore displays as **₹4.75 Lakhs**, and the *Medium* band shows its true
interval **₹3.99 – ₹6.75 Lakhs**.

### 🗂️ Categorical columns use a dropped baseline — and the app rebuilds it

The categorical columns are one-hot encoded **with a dropped baseline** (standard
practice to avoid the dummy-variable trap). Counting the data:

| Group | Columns present | Dropped baseline | Baseline share |
| :---- | :-------------- | :--------------- | :------------- |
| Seller | `Individual`, `Trustmark Dealer` | **Dealer** | **60 %** |
| Fuel | `Petrol`, `Diesel`, `Electric`, `LPG` | **CNG / Other** | ~1.6 % |
| Transmission | `Manual` | **Automatic** | ~20 % |
| Seats | `5`, `>5` | **Fewer than 5** | ~1.2 % |

Because the single most common seller category (**Dealer**, 60 % of cars) *is*
the dropped baseline, the app makes it a **first-class, selectable option** that
simply sets no flag (e.g. `Dealer → []`, `CNG → []`), faithfully reproducing the
exact one-hot encoding the model was trained on. The mapping lives in one place
(`SELLER_FLAGS`, `FUEL_FLAGS`, …) and is recorded in `metadata.json` rather than
hard-coded, so choosing "Dealer" or a "CNG" car produces an unbiased prediction.

Only `make` and `model` are free-text; they're one-hot encoded inside the
pipeline with `handle_unknown='ignore'`, so unseen values degrade gracefully.

## 3. Architecture: one metadata contract

The defining structural decision is that **`train_model.py` emits a
`metadata.json`** that fully describes the UI, and **the apps are driven entirely
by it**. The form can never fall out of sync with the model.

```
            train_model.py                         app.py / app_v1.py
  ┌───────────────────────────────┐      ┌──────────────────────────┐
  │ data/cars24-…-cleaned-new.csv │      │  loads 5 artifacts       │
  │            │                  │      │                          │
  │   clean → bin → fit RF×2      │      │  metadata.json ─┐        │
  │            │                  │      │   • makes→models │ builds │
  │   writes:  ▼                  │ ───► │   • slider ranges├─►form  │
  │   price_model.pkl             │      │   • categories   │        │
  │   range_model.pkl             │      │  range_config ──┘        │
  │   feature_columns.json        │      │   • bin edges + UNIT      │
  │   range_config.json (+unit)   │      │  price_model → ₹ exact    │
  │   metadata.json               │      │  range_model → Low/Med/Hi │
  └───────────────────────────────┘      └──────────────────────────┘
```

`metadata.json` contains:

* `makes_models` — `{ "MARUTI": ["SWIFT VXI", …], … }` for the cascading dropdown.
* `model_options` / `make_options` — the valid fuel / transmission / seats per
  model (and per make, as a fallback), so the dependent dropdowns can only ever
  offer real combinations. See **§6** and
  [INPUT_VALIDATION_GUIDE.md](INPUT_VALIDATION_GUIDE.md).
* `model_specs` / `make_specs` — median engine / power / mileage per model, for
  the simple app's auto-fill (see §5).
* `numeric_features` — outlier-robust slider bounds (1st–99th percentile),
  sensible step and default (median) per feature, plus dtype.
* `categorical_features` — the option lists **including the baselines** (used as
  the final fallback).
* `metrics` — R², MAE and accuracy, surfaced live in the sidebar.

A welcome side-effect: **the app doesn't need the CSV at runtime** — it's only
required for (re)training.

## 4. Modelling decisions

* **Two models, one feature set** — a `RandomForestRegressor` for the exact price
  and a `RandomForestClassifier` for the Low/Medium/High band. Both sit on a
  shared `ColumnTransformer` pipeline.
* **Why Random Forest** — for a tabular problem mixing numeric and ~3,200 one-hot
  columns, RF delivers strong accuracy (R² ≈ 0.95) with almost no tuning, is
  robust to outliers, needs no feature scaling, and ships inside scikit-learn.
  Gradient boosting (XGBoost / LightGBM / `HistGradientBoosting`) is the natural
  upgrade path for smaller, faster artifacts at the cost of more tuning and an
  extra dependency. The full DT-vs-RF-vs-XGB-vs-LGBM comparison is in the
  [README](../README.md#why-random-forest-dt-vs-rf-vs-xgboost-vs-lightgbm).
* **Tercile bands** (33rd/67th percentile) keep the three classes balanced
  (~33 % each), which is why the classifier uses `class_weight="balanced"`.
* **Bounded trees** (`max_depth=18`, `min_samples_leaf=4`) — see §5.
* Reported with **MAE in Lakhs** (≈ ₹0.71 L) alongside R² because "average error
  of ₹71,000" is far more intuitive to a car buyer than an R² value.

## 5. Compact, fast-loading artifacts

With ~3,200 one-hot `model` columns, unbounded Random Forests would both overfit
and produce very large pickles (deserialising a 100 MB+ file on first load can
look like a hang). **Bounding the trees** (`max_depth=18`,
`min_samples_leaf=4`) and **compressing the pickles** solves both at once — this
regularisation *also improves generalisation*:

| File | Size | Notes |
| :--- | ---: | :---- |
| `price_model.pkl` | **~13.5 MB** | `RandomForestRegressor` pipeline, zlib `compress=3` |
| `range_model.pkl` | **~1.0 MB** | `RandomForestClassifier` pipeline, zlib `compress=3` |

> **Companion project note (2026-07-09):** a Flask REST-API version of this same
> predictor (maintained in its own separate repository) pushed this
> further by benchmarking joblib's compression backends directly on these same
> artifacts (zlib, bz2, lzma, lz4, at multiple levels) and switching from zlib to
> **LZMA**: `price_model.pkl` → **8.9 MB**, `range_model.pkl` → **0.7 MB**, with
> load time actually *improving* over the zlib baseline. This project keeps the
> `compress=3` zlib setting; the same one-line
> `joblib.dump(..., compress=("lzma", 9))` change would apply here too if these
> artifacts ever need to shrink further.

## 6. Input model & UI/UX decisions

### A cascading Make → Model → specs form

There are **3,233 distinct models**, so instead of free text the app uses a
**cascading Make → Model dropdown**: selecting a brand filters the model list to
that brand's real variants, so every input is valid by construction. Because the
encoder uses `handle_unknown='ignore'`, this also guarantees a chosen model is
always one the encoder actually knows, so the prediction reflects the real car.

### Presentation

* **Wide, sectioned single-page layout** (`1 · Vehicle`, `2 · Specifications`)
  inside bordered cards (full edition, `app_v1.py`).
* **Sidebar** repurposed for an "About" blurb and **live model-quality metrics**.
* **Result cards** for the exact price and the band, plus a **three-band gauge**
  with a marker (`🔻`) showing exactly where the estimate sits on the price scale.
  The classifier's band is highlighted; the marker comes from the regressor.
* All money rendered with `format_lakhs()` so ₹, Lakh and Crore are consistent
  everywhere (the sidebar MAE, the cards, the gauge labels).

Trained on **19,820 cars / 41 brands** (held-out 20 % test set):

| Metric | Value |
| :----- | :---- |
| Price R² | **0.950** |
| Price MAE | **₹0.71 Lakhs** |
| Band accuracy | **76.9 %** |

Spot-checks (exact predictions from the saved model):

| Car | Prediction | Band |
| :-- | :--------- | :--- |
| Maruti Swift VXI · Petrol · Individual | ₹5.24 Lakhs | Medium |

| Maruti Wagon R · **CNG** · Individual | ₹3.35 Lakhs | Low |

The CNG and Dealer cases confirm the baseline categories work end-to-end.

## 8. Simple edition — `app.py`

A second front-end built for **demos to complete beginners**: *simplicity is the
ultimate sophistication*. Same trained models, a radically smaller surface.

**What it drops** (vs the full `app_v1.py`): the custom CSS, gradient hero,
result cards, the gauge, the sidebar, expanders and the debug table — i.e.
everything ornate. Only plain Streamlit widgets remain (`selectbox`, `slider`,
`radio`, `metric`). There is also **no "Predict" button**: the estimate updates
**live** as inputs change, which is both simpler and more engaging to watch.

**What it hides** — a novice can't answer "engine cc" or "max power bhp", so the
form asks only six intuitive questions (brand, model, fuel, gearbox, age, km).

**The key decision — auto-filling the hidden specs.** Engine and power are *strong*
price predictors, so they can't just be dropped. Filling them with one **global
median** would collapse premium cars toward the average:

| Car | global-median fill | per-model fill | actual |
| :-- | -----------------: | -------------: | -----: |
| BMW X5 | ₹8.2 L ❌ | **₹20.7 L** ✅ | ₹20.8 L |
| Toyota Fortuner | ₹7.7 L ❌ | **₹18.5 L** ✅ | ₹20.0 L |

So `train_model.py` records **per-model (and per-make) median specs** in
`metadata.json` (`model_specs` / `make_specs`), and the simple app auto-fills from
the *chosen model's* typical values — "you picked the model, so we know its
specs." Lookup falls back per-model → per-make → global. The form stays trivially
simple while predictions stay accurate across the whole price range.

Run it with: `streamlit run app.py`.

## 9. Preventing invalid inputs (the validated-data approach)

The data is clean and finite, so rather than *validating* user input we make
invalid input **unrepresentable** — the form only ever offers values that exist
in the data. The full, beginner-oriented write-up is in
[INPUT_VALIDATION_GUIDE.md](INPUT_VALIDATION_GUIDE.md); the engineering summary:

* **Intrinsic vs circumstantial inputs.** Attributes that belong to the *car*
  (fuel, transmission, seats, engine, power, mileage) are derived from the chosen
  **model**; attributes about the *sale* (seller, age, km) stay free within data
  bounds. A `SWIFT VDI` is always diesel; any car can be 5 years old.
* **Dependent dropdowns.** `model_options[make][model]` lists the fuel /
  transmission / seats actually seen for that model. The full app limits those
  dropdowns to it; the simple app auto-selects `[0]` and shows it read-only.
  Result: combinations like "Electric Alto" cannot be entered. 3,231 / 3,233
  models have a single valid fuel and gearbox anyway (the variant name encodes
  them), so this is mostly *automatic selection*, not a choice.
* **No stale state.** The cascading widgets (`model`, `fuel`, …) are intentionally
  given **no `key=`**, so each rerun rebuilds them from the current parent
  selection. Changing the brand can't leave a mismatched "Maruti X5" behind —
  data only flows downhill (make → model → fuel/gearbox/seats).
* **Single source of truth.** All these lists come from `metadata.json`, written
  by `train_model.py`, so the form can never drift from what the model was
  trained on. Retraining refreshes the form automatically.

## 10. Known limitations / future work

* **Band accuracy (~77 %)** is capped by the arbitrary tercile boundaries — cars
  near a boundary are genuinely ambiguous. One could instead **derive the band
  from the (very accurate) predicted price** to guarantee the band and the rupee
  figure never disagree; this design keeps a separate classifier to honour the
  two-model design.
* Slider bounds are clipped to the 1st–99th percentile, so extreme inputs (e.g. a
  brand-new car with <3 years age) can't be entered. Widen the percentiles in
  `train_model.py` if needed.
* `model` cardinality is high (~3,200). Target/frequency encoding — or a switch
  to gradient boosting — would shrink the artifacts further and likely help the
  rarer models, at the cost of a more complex pipeline.
